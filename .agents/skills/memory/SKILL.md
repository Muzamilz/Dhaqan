# Memory

Memory here is deliberately simple: one append-only markdown file per
project, human-readable, git-trackable, no database. The goal is durable
project knowledge, not a clever retrieval system.

## Invocation

Model-invoked from other skills when something worth remembering comes up
(a non-obvious decision, a gotcha, a constraint discovered mid-task). Also
user-invoked directly in four modes: `/memory` (review), `/memory add
<note>` (append to project memory), `/memory promote` (run the promotion
workflow toward the global vault), `/memory evaluate` (analyze memory for promotion candidates with reasoning).

## Obsidian awareness

If Obsidian MCP tools are present in the current session, use them to read
and write vault notes directly — search/read/create/append, whatever the
connected server exposes. Note that Obsidian is an interface/storage layer
for knowledge (not an agent layer) — it provides views of Markdown files
but does not execute tasks or modify project state. If MCP tools are not
present, fall back to the local `.org/memory/project-memory.md` file and
tell the user the vault side needs a manual copy (see
`.vault-template/ARTIFACT-SYNC-MAP.md`). Never assume MCP tools exist —
check the actual tool list each time, since the person may not have the
connection active in every session.

## Reading

At the start of any non-trivial task (`/implement`, `/architect`), read
`.org/memory/project-memory.md` in full — it should stay small enough that
this is cheap. If it's growing past a page or two, that's a signal to prune:
propose moving stale entries into the relevant `.org/artifacts/` file where
they're more specifically useful, and trim memory back down.

## Optional: codebase-graph (structural memory)

If `.org/memory/codebase-graph/index.md` exists, it holds structural
knowledge about the codebase — imports, dependencies, module communities —
generated by an external tool (Graphify), not by this kit. This is a
**different kind of memory than project-memory.md**: it captures what the
code IS, not what was decided or why. Treat the two as complementary:

- Use `project-memory.md` for decisions, gotchas, and reasoning.
- Use `codebase-graph/` (when present) to answer "what does this touch,
  what imports this, what else lives in this module's neighborhood" instead
  of re-reading files to reconstruct that by hand.

This kit does not generate or maintain `codebase-graph/` — that's the
user's responsibility, run outside these skills (e.g. `graphify --wiki`
pointed at `.org/memory/codebase-graph/`). Graphify is optional and runs
externally. If the directory doesn't exist, skip this step entirely;
nothing in this kit requires it.

## Writing

Append entries as a dated bullet, not a prose paragraph:

```
## 2026-08-02
- Decided to use Postgres over SQLite for the metrics store — needed
  concurrent writes from two workers. See architecture-t4.md.
- Gotcha: the vendor API rate-limits at 60 req/min, not the documented 100.
```

Never rewrite or delete past entries — this is append-only. If something
becomes wrong or outdated, add a new entry that supersedes it and says so
explicitly, rather than editing history.

## Friction signals (feeds organization evolution)

If a task required an engineer to act outside its documented Scope, or a
workflow step didn't fit how the work actually happened, tag the entry
`[friction]` and name which engineer/workflow it concerned:

```
- [friction: backend-engineer] Asked to make a frontend styling call —
  outside Scope, but no frontend engineer exists yet for this project.
```

Don't act on a single friction entry by proposing an organization change
yourself — that's `/bootstrap-org`'s job on its next human-invoked run,
which looks for a *pattern* of repeated friction against the same
engineer/workflow, not one-off incidents.

If it's a decision with a clear write-up already (architecture doc, spec),
memory should just link to it, not duplicate it. Memory is for the *loose*
knowledge that doesn't have a natural home elsewhere — the stuff that would
otherwise get lost when a session ends. Global memory (via promotion below)
is for the subset of that knowledge that would help a *different* project
too.

## Promotion mode (`/memory promote`)

This is the path from project-local memory to the durable global vault
(`00-global/`). Nothing enters global memory automatically — every
promotion goes through this workflow, and it always stops for human
approval before the last step:

```
Observation          — something in project-memory.md or a recent artifact
    ↓
Evaluation            — is this actually reusable beyond this one project,
                         or is it specific to this project's quirks?
    ↓
Candidate memory      — draft the note using the matching template from
                         the global vault's templates/ (principle,
                         pattern, decision, or lesson), status: candidate
    ↓
Classification        — which category folder it belongs in
    ↓
STOP — show the candidate to the user, explicit approval required
    ↓
Stored                — status: promoted, written to 00-global/<category>/,
                         linked back to the project note it came from
```

Run this periodically, or when a decision feels reusable enough to flag —
don't try to promote everything, and don't promote silently even if it
seems obviously reusable.

## Evaluation mode (`/memory evaluate`)

Analyzes project memory entries and suggests promotion candidates with
reasoning, making promotion decisions more intelligent and less reliant on
pure human judgment.

**Process:**
1. Scans `.org/memory/project-memory.md` for entries that are:
   - At least 7 days old (to avoid premature promotion)
   - Not already tagged as promoted or evaluated
   - Contain specific decisions, gotchas, or constraints (not just meeting notes)
2. For each candidate entry, provides:
   - **Reusability score** (1-5): How useful this would be to other projects
   - **Reasoning**: Why it scored that way (specificity, lack of project assumptions, clarity)
   - **Suggested template**: Which vault template (principle, pattern, decision, lesson) fits best
   - **Draft note**: A promoted version with any project-specific references generalized
3. Outputs a prioritized list of candidates with scores and reasoning
4. User can then run `/memory promote` on specific entries with confidence

**Example output:**
```
## Memory Evaluation Results (2026-09-05)

🥇 HIGH PRIORITY (Score: 5)
- Entry: "## 2026-08-02\n- Decided to use Postgres over SQLite for the metrics store — needed concurrent writes from two workers."
- Reasoning: Specific technical decision with clear rationale, generalizable to any project needing concurrent writes, references external doc
- Suggested template: decision
- Draft note: 
  ```
  ---
  type: decision
  scope: global
  status: candidate
  date: 2026-08-02
  tags: [database, concurrency, technology-choice]
  confidence: observed
  ---
  
  ## What
  Choose Postgres over SQLite when concurrent writes from multiple workers are needed.
  
  ## Why it matters
  SQLite handles concurrent writes poorly due to database locking, leading to failed transactions and poor performance under load.
  
  ## How to apply it
  For any service handling concurrent writes from 2+ workers, evaluate Postgres as primary choice. Consider connection pooling and proper transaction isolation levels.
  
  ## Related
  [[technology-selection-pattern]] [[database-concurrency-pattern]]
  ```

🥈 MEDIUM PRIORITY (Score: 3)
- Entry: "## 2026-08-10\n- Gotcha: the vendor API rate-limits at 60 req/min, not the documented 100."
- Reasoning: Specific gotcha with clear impact, but somewhat vendor-specific; could be generalized to "always verify external API limits empirically"
- Suggested template: pattern
- Draft note: ...
```

**Usage:**
- `/memory evaluate` - Run full evaluation and see suggested candidates
- `/memory evaluate --min-score 4` - Only show candidates scoring 4 or higher
- `/memory evaluate --since 2026-08-01` - Only evaluate entries since a specific date

## Completion criteria

For a project-scoped write: the entry is dated, specific, and doesn't
duplicate content that already lives in an artifact. For a promotion: the
candidate was shown to and explicitly approved by the user before being
written to the global vault — never promoted on inference alone. For a
read: the calling skill actually used what was relevant, not just
acknowledged the file exists. For an evaluation: the analysis provides
specific, actionable reasoning for each candidate, not just vague
recommendations.
